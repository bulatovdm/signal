# 2026-10-16 — Задание: неделя статистики туннелей глазами роутера

Пришло из `veil` (сессия `tunnel-fallback`, журналы `veil` 2026-10-16-01…03, ADR-037…042).
По её словам, Дмитрий согласовал, что делается в `signal`. Здесь не начато: ждёт подтверждения
Дмитрия в сессии `signal`.

## Зачем

Дмитрий работает на TimeWeb: обе карты Mac Studio в `Policy3`. Терять неделю данных по VDSina он не
хочет. Нужен фоновый наблюдатель: работает, пока Mac включён, переживает перезагрузку (launchd, как
пульс), через неделю даёт отчёт.

## Как мерить: роутер пингует сам, политику Mac не трогаем

Сторож роутера и политики не менять (`veil` ADR-042: выход меняет только Дмитрий вручную). Mac
просит роутер пингнуть через конкретный туннель:

`POST /rci/` с `[{"parse":"tools ping <host> count 3 source-interface <iface>"}]`

Проверено `veil` в 18:1x, Mac в `Policy3`:

| Туннель | Цель | RTT |
|---|---|---|
| `Wireguard1` (вход VDSina) | `10.60.0.1` (сам вход) | 17,7 мс |
| `Wireguard1` | `10.30.0.1` (выход VDSina) | 52,6 мс |
| `Wireguard3` (запасной вход TimeWeb → выход VDSina) | `10.30.0.1` | 46,9 мс |
| `Wireguard2` (TimeWeb) | `10.30.0.1` (выход TimeWeb) | 37,8 мс |

Цели раз в ~10 с: W1→10.60.0.1, W1→10.30.0.1, W3→10.30.0.1, W2→10.30.0.1. Пара проб через W1
разделяет поломку «вход VDSina → дом» и плечо «вход → Амстердам».

## Ловушки RCI, проверенные `veil`

- Вывод `tools ping` приходит обрезанным (`"continued": true`), по сути только первый ответ.
  Ping без ответов ошибкой RCI **не** считается. Успех — по `bytes from` в `.parse.message[]`,
  RTT — оттуда же (`time=`). Для потерь лучше `count 1` много раз, чем один `count 3`.
- Кука ротируется на каждом ответе — писать обратно (`-b` и `-c` на один jar). Готовая
  реализация: `veil/scripts/lib/keenetic.sh` (`keenetic_rci_login`, `keenetic_rci_parse_show`).
- Журнал роутера: `{"parse":"show log 600"}` работает; `show log max-lines N` — `argument parse
  error`. (В `signal` сейчас журнал берётся POST `{"show":{"log":{"max-lines":N}}}` — работает.)
- Переключения сторожа в журнале: `"Wireguard1": "ping-check" changed "ipv4" layer state
  "running" to "pending"` (ушёл на W3) и `... "pending" to "running"` (вернулся).
- Профиль `ping-check veil-tunnel` **не трогать**: любая правка (привязка, хост) сама вызывает
  переключение на ~25 с, а `no host <addr>` удаляет все хосты.
- Вход TimeWeb (`10.60.0.1` через `Wireguard2`) роутеру сейчас не отвечает — та же
  geosplit-причина, что днём была у VDSina; узкое правило на `<ru-timeweb>` предложено Дмитрию,
  не согласовано. До тех пор у W2 только проба выхода.

## Ещё писать

- Трафик по туннелям: `show interface WireguardN`, rxbytes/txbytes — отличать перегрузку от
  обрыва (днём «обрывы» оказались торрентом на 90–100 Мбит/с).
- Активный маршрут `Policy2` и `Policy3`: `show ip policy`, `route4.route[]` с `destination ==
  "0.0.0.0/0"` (в `signal` уже есть `router_policy_active`).
- Счётчики `ping-check` (`/rci/show/ping-check`, профиль `veil-tunnel`) — в `signal` уже есть
  `router_ping_check`.
- Со стороны серверов уже есть `path-watch` на входах (`veil` ADR-035): раз в минуту возраст
  рукопожатия дома, kB к дому и из дома, маршрут, 14 дней в `/var/log/veil/path-watch.log`;
  сводка за сутки — `veil-path-watch.sh summary` на ноде. Подтягивать при отчёте; адреса нод в
  `signal` не хардкодить — они в пресетах `veil`.

## Отчёт через неделю

По каждому туннелю: доступность в %, список обрывов (начало, длительность, участок: вход → дом /
вход → выход), RTT p50/p95 в обычное время и под нагрузкой, переключения сторожа (сколько,
длительность ухода), сравнение VDSina и TimeWeb. Плюс суточная сводка одной строкой.

## Контекст дня из `veil`

- Узкое место VDSina — сам выход `<am-vdsina>`: 87 Мбит/с и 17–25% потерь с любого входа против
  183 и 0% у TimeWeb.
- Сторож W1 пингует `10.60.0.1`, 4 с × 6 промахов (~30–40 с до ухода), возврат ~27 с.
- `veil provision qos`: CAKE 100/130 на плечах VDSina.

## Заметки `signal` к будущему решению

- Ближе всего к наблюдателю туннеля (ADR-016) и пульсу (ADR-017); решить при старте — новый
  демон или расширение одного из них, с ADR.
- Пробы идут через `tools ping` роутера — это не «только чтение» роутера в строгом смысле
  (роутер выполняет команду), но его состояние не меняют; зафиксировать это в ADR.

## Дополнение 20:3x — вход TimeWeb отвечает роутеру

`veil` (Дмитрий согласовал, `veil provision fallback servers`, ADR-038 `veil` расширен): узкое правило
теперь стоит и на `<ru-timeweb>`. Цели наблюдателя — по две на туннель, все проверены роутером в 20:3x:

| Туннель | Вход (участок «вход → дом») | Выход (участок «вход → выход») |
|---|---|---|
| `Wireguard1` (VDSina) | `10.60.0.1` — 10,9 мс | `10.30.0.1` — выход VDSina |
| `Wireguard2` (TimeWeb) | `10.60.0.1` — 2,1 мс | `10.30.0.1` — выход TimeWeb |
| `Wireguard3` (запасной вход → выход VDSina) | `10.61.0.1` — 3,2 мс (сам `awg2`) | `10.30.0.1` — выход VDSina через запасное плечо |

Побочный эффект для пульса: `traceroute` с Mac в `Policy3` теперь показывает вход TimeWeb
`10.60.0.1` вторым хопом (раньше `*`) — точка «входной сервер» пульса для `Policy3` заработала.

`veil` согласна: журнал роутера — POST `{"show":{"log":{"max-lines":N}}}`, активный маршрут и
`ping-check` — `router_policy_active` и `router_ping_check` из `lib/router.sh`.
